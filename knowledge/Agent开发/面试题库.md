# Agent 开发岗面试题库

### 1. 工具调用与接口设计

#### Q002 · 工具调用与接口设计 · 状态：已分析
**题目**：Ontology 相较于传统数据库 Schema、数据模型和暴露 API 的差异是什么？
**关联**：Q003 判断本体适用条件。
**考什么**：能否区分数据的存储结构、业务含义和可执行操作。
**解题思路**：
1. 用同一个业务事实分别解释三种表示。
2. 说明哪一层负责映射，哪一层执行操作。

**参考答案**：拿一次面试来说，数据库 Schema 可以用外键把面试记录连到申请表，API 可以提供查询面试安排的操作。本体可以给“候选人”“申请”“岗位”统一定义，并明确一次面试针对某次申请，同一个人可以有多次申请。这样跨招聘和日历系统查询时，各方可以复用同一条关系。底层仍需要维护对象到真实记录的映射，还要由服务执行鉴权和查询。

#### Q003 · 工具调用与接口设计 · 状态：已分析
**题目**：已经有 MCP 工具和 Skill，为什么还需要 Ontology？是否存在 Agent 任务能力上的实质差异？
**关联**：Q002 关注概念边界，本题比较维护收益。
**考什么**：能否判断本体带来的实际增量。
**解题思路**：
1. 先设计一个只靠工具和技能说明也能完成的任务。
2. 换一个使用同一业务关系的场景，比较维护代价。

**参考答案**：查询某岗位的待面试名单，用 MCP 暴露查询工具、用 Skill 说明调用顺序就可以完成。多个团队还要根据同一套“有效申请”定义统计漏斗、发通知时，如果规则散落在技能说明里，更新一次就要逐份核对。本体可以集中表达对象关系与业务定义，让不同工具引用同一语义。若只有单一流程，接口约定已经稳定，我会先沿用现有工具，等重复维护的成本出现再引入本体。

#### Q008 · 工具调用与接口设计 · 状态：已分析
**题目**：Chat Completions/Responses API 中，正文 text 与 tool_calls 是什么关系？
**关联**：Q009 处理信号冲突。
**考什么**：能否从真实响应结构提取正文和待执行调用。
**解题思路**：
1. 分别识别两套 API 的输出位置与关联 ID。
2. 把展示文本和工具请求转换为独立的运行时事件。

**参考答案**：Chat Completions 中我会分别读取 assistant 消息的 content 和 tool_calls，用每个调用的 id 对应工具消息里的 tool_call_id。Responses 则遍历 output，分别处理 message 中的文本和 function_call 项，回传 function_call_output 时使用对应的 call_id。一轮输出可能带有解释文字和待执行调用，所以判断能否结束还要检查调用列表和响应状态。流式接收时要等参数完整后再解析和执行。


### 2. 任务规划与工作流

#### Q001 · 任务规划与工作流 · 状态：已分析
**题目**：从零做 Agent，你怎么看 Java 和 Python 的优势、劣势和选型？
**关联**：Q007 展开 Java 实现。
**考什么**：语言选型能否落到交付条件上。
**解题思路**：
1. 列出主要耗时、现有服务和团队维护成本。
2. 用同一条调用链验证关键依赖与部署假设。

**参考答案**：如果招聘服务已经用 Java，有成熟的鉴权、监控和发布流程，我会优先用 Java 实现在线执行循环。模型请求通常需要等待网络，把循环换成 Python 并不会直接消除这段延迟。如果主要工作是离线评测、快速试验模型库，Python 则更容易复用现有脚本。我会用同一组任务比较流式调用、取消、并发和故障排查成本，再决定是否值得多维护一套服务。

#### Q004 · 任务规划与工作流 · 状态：已分析
**题目**：简历 PDF 与结构化字段如何处理？教育 Gap 怎么做确定性判断？
**关联**：Q005 从规则走向误差评估。
**考什么**：能否将文档抽取的不确定性与规则计算分开。
**解题思路**：
1. 记录每段教育经历的证据、日期精度和字段冲突。
2. 定义日期区间、阈值和无法判断时的出口。

**参考答案**：模拟处理简历时，我会把 PDF 抽取结果和结构化字段都转成带来源的教育经历，保留原始日期。如果规则按月计算，就先统一月份口径，合并重叠经历，再数两段之间完整空出的月份。仅写年份或两处日期矛盾时，输出待核实并附证据位置。回归用例覆盖月份相接、跨年、重叠和缺失，规则输出仅描述材料中的时间间隔。

#### Q007 · 任务规划与工作流 · 状态：已分析
**题目**：如果用 Java 自己写一个基础 Agent Loop，你会如何设计输入、循环、工具调用及结束条件？
**关联**：Q008 细化模型输出，Q009 检查退出。
**考什么**：能否在 Java 中明确状态所有权和循环退出条件。
**解题思路**：
1. 定义消息、工具请求和终态，隔离模型与工具执行器。
2. 走完正常调用、协议异常和预算耗尽三条路径。

**参考答案**：我会让 Java 的 Runner 持有消息历史、步数和截止时间，模型适配器把一次响应转成可枚举的事件。每轮先检查预算，再请求模型；遇到工具调用就按注册表校验名称、权限与参数，执行后用调用 ID 写回结果，再进入下一轮。没有待处理调用且拿到有效最终回答时返回成功。取消、超时、步数耗尽或协议无效分别返回可识别的终态，调用方可以区分结果和失败原因。

#### Q009 · 任务规划与工作流 · 状态：已分析
**题目**：tool_calls 非空但最终回答标记为 true 时，你的 Loop 怎么处理？
**关联**：Q007 定义循环，本题验证状态转换。
**考什么**：能否让冲突的状态信号走向确定且可测的出口。
**解题思路**：
1. 界定 final 标记属于哪一层，以及合法的状态组合。
2. 用冲突样本检验用户输出与工具副作用。

**参考答案**：我会在适配层规定终态要求所有工具调用已经处理完。若一次响应同时声明最终回答并要求执行工具，就先记为协议冲突，保留调用记录，暂缓提交回答和执行工具，然后在预算内要求模型给出一致的下一步。再次冲突则返回明确的失败状态。测试时我会断言用户没有提前收到成功结果，有副作用的工具也没有在纠正和重试期间重复执行。


### 3. 上下文与记忆管理

#### Q010 · 上下文与记忆管理 · 状态：已分析
**题目**：工具一次返回 500K、模型上下文只有 200K，该怎么办？
**关联**：Q012 展开分块。
**考什么**：能否在构建模型请求前限制单次工具结果。
**解题思路**：
1. 先确认 K 的计量单位，再扣除已有输入和输出预留。
2. 完整结果留在外部，模型先读概要并可按需取回证据。

**参考答案**：我会先确认 500K 指字节、字符还是 token，用目标模型的计量方式估算可用预算。原始结果流式写入受访问控制的存储，工具消息里保留结果句柄、规模和有界预览。比如一次查询返回大量记录，可以先返回统计和分页游标，让模型按任务需要取特定行，每次取回也设上限。截断或采样要明确标记，避免模型把预览当成全部结果。

#### Q011 · 上下文与记忆管理 · 状态：已分析
**题目**：多轮调用把整个 history 撑爆后，怎么处理？如果第一次压缩后历史仍然超过窗口，怎么处理？
**关联**：Q010 处理单次结果，本题处理历史。
**考什么**：能否在多轮压缩后仍然保证下一次请求可提交。
**解题思路**：
1. 把必须保留的指令、未完成调用与可外置历史分开。
2. 重算压缩后的实际预算，设置有限次数和最终出口。

**参考答案**：我会先保留系统约束、当前用户目标、未完成任务，以及继续执行所需的调用与结果配对。已完成轮次可以转成带证据引用的任务摘要，原始消息另存。第一次压缩后按实际请求重新计量，仍超限就外置大附件、收紧旧摘要，只取当前步骤需要的事实。如果必要输入加输出预留仍放不下，就拆成独立子任务或报告预算不足，避免反复压缩同一段历史。

#### Q012 · 上下文与记忆管理 · 状态：已分析
**题目**：如果用于压缩的小模型同样只有 200K 窗口，怎么处理 500K 的工具输出？
**关联**：Q010 估算输入，本题分层归并。
**考什么**：能否解释小模型第一次实际读到什么。
**解题思路**：
1. 为提示词、元数据和摘要输出留空间，再确定块大小。
2. 逐块抽取可追溯证据，归并时继续执行同一预算检查。

**参考答案**：上游数据先由程序读取，按记录或段落边界切块。假设每次只送一批记录，小模型第一次收到的是任务说明、这批记录和来源范围，输入连同输出预留必须落在 200K 内。每块产出结论、例外和原文位置，若这些摘要拼起来仍超限，就分批归并到下一层。涉及精确计数时交给程序聚合，涉及跨块引用时按记录 ID 回读原文。

#### Q013 · 上下文与记忆管理 · 状态：已分析
**题目**：按特定业务字段精简返回结果，如何做到真正通用？
**关联**：Q012 解决大小限制，本题划分通用职责。
**考什么**：能否让通用预算机制与领域裁剪策略独立演进。
**解题思路**：
1. 找出所有工具都能遵守的结果协议。
2. 把依赖业务语义的抽取交给可替换的工具适配器。

**参考答案**：我会让 Runtime 统一管理大小估算、预算、结果句柄、分页和回读权限。招聘工具可以额外声明按教育经历投影字段，财务工具可以声明按凭证号筛选；框架只处理适配器声明的能力和返回值。没有适配器时仍能保存原文、按块读取并标记截断。验收时接一项全新的工具，检查核心循环能否直接运行，以及每个返回片段能否追溯到原始结果。

#### Q014 · 上下文与记忆管理 · 状态：已分析
**题目**：平时主要用什么 Coding Agent？是否注意到 Codex 的上下文压缩机制？
**关联**：Q011 设计历史压缩，本题检验产品行为。
**考什么**：能否区分亲自观察的产品行为与对实现的推测。
**解题思路**：
1. 先说实际用过的工具、版本和任务。
2. 用可重复任务检查压缩后保留的信息及需要回读的内容。

**参考答案**：我会先按自己的真实使用情况回答。若要检验 Codex 的上下文压缩，可以在长会话前段约定接口名称、验收命令和一个例外条件，记录这些约束是否只出现在对话里。观察到压缩后，再让它复述约束并继续修改，分别核对它直接保留了什么、哪些内容是重新读文件找回来的。回答时注明版本与观察条件；具体触发阈值、摘要格式等内部细节应以对应版本的公开实现为依据。


### 4. 失败恢复与效果评测

#### Q005 · 失败恢复与效果评测 · 状态：已分析
**题目**：早期模型为什么有误判和漏判？为什么调整 P0/P1 等需求优先级？
**关联**：Q006 用评测检验优先级。
**考什么**：能否用可复现的错误和业务损失解释排期。
**解题思路**：
1. 明确统计单位与分母，分开核查误报和漏报。
2. 按影响面、后果和可恢复性给出优先级。

**参考答案**：我会拿经复核的样本按规则列出误报、漏报和判断正确的数量，同时写清分母是候选人、字段还是规则命中次数。再从错误样本回放输入、抽取、规则和最终展示，确认最早出错的位置。模拟排期时，若某项漏报会让整批材料跳过必要复核，我会提议优先修；有明显提示且能在复核中纠正的展示误差可以后排。实际项目应给出团队约定和当时的样本依据。

#### Q006 · 失败恢复与效果评测 · 状态：已分析
**题目**：如何调试 Code/LLM 节点？如何做端到端评测，有没有自动化跑分？
**关联**：Q005 讨论误差成本，本题复现实例。
**考什么**：能否定位节点故障并验证整条工作流。
**解题思路**：
1. 保留脱敏输入、节点版本和中间输出，用固定样本回放。
2. 分开验证确定性逻辑、模型输出及端到端效果。

**参考答案**：我会从失败任务中截取最先偏离预期的节点输入。Code 节点用固定输入断言字段和错误路径，LLM 节点固定提示词与模型配置，按人工标注的字段和证据打分，对不稳定样本重复运行。随后用同一批脱敏数据跑完整流程，比较误报、漏报、耗时和费用。新增回归用例要能在旧版本复现问题，在修复后通过，评测结果按版本保存。
