# 前端开发岗面试题库

### 1. 浏览器与网络

#### Q001 · 浏览器与网络 · 状态：已分析
**题目**：讲一下 SBridge 的原理。
**关联**：Q002 讨论能力边界，本题追踪一次桥调用。
**考什么**：能否追踪一次 H5 调用原生功能的往返过程。
**解题思路**：
1. 先确认 SBridge 的项目定义和调用入口。
2. 以一次扫码请求串起消息、分发、返回和异常清理。

**参考答案**：我会先确认这里的 SBridge 是否指项目封装的 JSBridge。以常见的异步扫码接口为例，H5 给请求分配 ID，保存对应的 Promise 回调，再通过 WebView 提供的消息通道把方法名和参数交给原生端。原生端校验页面来源、方法权限和参数，扫码结束后把结果连同 ID 回传。H5 用 ID 找回等待的调用，完成或拒绝 Promise，并清理回调。SBridge 的具体通道和消息格式需要看项目实现。

#### Q004 · 浏览器与网络 · 状态：已分析
**题目**：讲下流式渲染。
**关联**：Q012 描述导航全程，本题关注增量呈现。
**考什么**：能否解释数据分批到达后，用户为何能提前看到内容。
**解题思路**：
1. 先确认是服务端流式 HTML，还是页面内的流式输出。
2. 分别追踪第一块内容何时可见，以及哪里可能积压。

**参考答案**：如果问服务端渲染，我会先发包含页面骨架的 HTML，把等待慢数据的区域留出占位，后续内容就绪后再逐步送达。浏览器可以边接收边解析，可见时间还受样式和代理缓冲影响。如果问聊天回答，则可以逐段读取响应体，用流式解码器保留跨块字符，再按协议边界拼出完整消息、批量更新文本。验证时我会分别记录首字节和第一段内容真正出现在屏幕上的时间。

#### Q005 · 浏览器与网络 · 状态：已分析
**题目**：发起请求后，如何实现请求取消？
**关联**：Q006 比较其他取消机制。
**考什么**：能否把请求的生命周期和界面状态正确关联。
**解题思路**：
1. 把控制器交给知道何时应取消请求的组件。
2. 逐项处理取消、迟到结果与界面清理。

**参考答案**：用 fetch 做搜索时，我会给每次请求创建一个 AbortController，把 signal 传给 fetch，新关键词到来或组件卸载时调用对应控制器的 abort。读响应体也可能在取消时失败，所以请求和读取过程都要处理异常，用户主动取消无须显示网络错误。为防旧请求的清理逻辑覆盖新状态，我会检查请求标识再更新列表和 loading。客户端取消后，服务端已经开始的工作仍可能继续。

#### Q006 · 浏览器与网络 · 状态：已分析
**题目**：除了 AbortController，还有哪些取消请求的方案？
**关联**：Q005 说明标准取消流程，本题比较替代手段。
**考什么**：能否区分中止传输、忽略结果和取消服务端任务。
**解题思路**：
1. 先看请求由什么 API 发出。
2. 再明确要节省网络资源、避免旧数据覆盖，还是终止后台工作。

**参考答案**：如果请求本来由 XMLHttpRequest 发出，可以保留实例并调用 xhr.abort()。如果现有封装只暴露 Promise，我可以用递增的请求编号丢弃过期响应，解决搜索结果乱序，但底层传输仍会进行。Promise.race 加超时时也有这个限制。对于已经返回任务 ID 的长时间导出，要让后端提供取消接口，并由执行任务的进程检查取消状态，前端才能展示真实的取消结果。

#### Q010 · 浏览器与网络 · 状态：已分析
**题目**：介绍重排与重绘，开发中有哪些写法可以减少性能损耗？
**关联**：Q012 涵盖首次布局，本题分析更新成本。
**考什么**：能否用一次读写 DOM 的例子解释布局与绘制成本。
**解题思路**：
1. 区分几何变化与仅影响外观的变化。
2. 找出强制同步布局的读写顺序，用性能记录验证。

**参考答案**：改宽度可能影响后续元素的位置，浏览器需要重新计算布局，再绘制受影响的区域。只改文字颜色通常可以沿用原来的几何信息，重新绘制像素即可。一个常见慢点是在循环里写入样式后马上读 offsetWidth，读操作为了拿到最新尺寸，可能迫使浏览器反复同步布局。我会先集中读取所需尺寸，再批量写入；位移动画可优先考虑 transform，最后看性能记录里的布局次数和耗时是否下降。

#### Q012 · 浏览器与网络 · 状态：已分析
**题目**：输入 URL 到页面渲染完成，浏览器完整经历了哪些流程？
**关联**：Q010 深入布局和绘制，本题串联导航全过程。
**考什么**：能否按依赖关系说明导航、资源加载与屏幕首次呈现。
**解题思路**：
1. 从导航请求讲起，指出哪些阶段可以因缓存或连接复用而省略。
2. 顺着 HTML 到像素解释阻塞点，明确所说的完成时刻。

**参考答案**：以打开一个 HTTPS 页面为例，浏览器解析 URL，检查可用缓存，必要时解析域名、建立安全连接，发送请求并处理重定向。HTML 可以边到达边解析成 DOM，浏览器同时发现样式、脚本和图片，阻塞型脚本可能暂停解析。样式就绪后，浏览器计算元素样式和布局，绘制内容，再合成到屏幕。用户看到首屏、DOMContentLoaded 触发和 load 触发是不同的观察点，异步数据还可能在 load 后继续改变页面。

### 3. 框架与组件

#### Q002 · 框架与组件 · 状态：已分析
**题目**：项目同时包含 Web 端与 App 内嵌 H5，哪些功能可以复用，哪些无法复用？
**关联**：Q003 关注上线，本题先划分复用边界。
**考什么**：能否按运行环境的依赖拆分共享代码。
**解题思路**：
1. 挑一个两端都有的业务流程，逐层检查其依赖。
2. 给容器差异设计统一入口，并说明缺少能力时的体验。

**参考答案**：以资料编辑页为例，字段校验、提交状态和错误展示都可以共享。选头像这一步，两端可以共用预览组件和上传逻辑，但取照片要看容器提供什么能力。浏览器可以使用文件选择器，App 可能要求通过原生相册取得受限的文件标识。我会给页面提供统一的选图接口，由适配层把两端结果转换为上传模块能处理的数据，并单独处理拒绝授权和用户取消。

#### Q007 · 框架与组件 · 状态：已分析
**题目**：封装组件时会从哪些维度考虑，整体思路是什么？
**关联**：Q008 以长列表为具体组件案例。
**考什么**：能否把组件的使用场景转成清楚、可测试的接口。
**解题思路**：
1. 用两个调用场景找出稳定行为及差异。
2. 定义状态归属、交互出口和可验证的边界。

**参考答案**：假设要封装一个搜索选择器，可以先看单选表单和远程搜索页分别需要什么。选中值由父组件持有，组件接收选项并发出选择事件，展开和键盘高亮留在内部。加载、无结果和错误要有明确的展示位置，调用方需要自定义选项外观时再开放插槽。验收时我会用键盘完成一次选择，再测清空、禁用和异步更新选项，确认焦点和选中值都符合接口约定。

#### Q008 · 框架与组件 · 状态：已分析
**题目**：基于 Vue Virtual Scroller，简述虚拟滚动的实现原理。
**关联**：Q007 讨论组件接口，本题解释窗口计算。
**考什么**：能否从滚动位置推导可见数据，并解释视图复用。
**解题思路**：
1. 先算固定行高的窗口，再解释滚动条如何保持总高度。
2. 补充行高变化时的定位方法和复用后的状态管理。

**参考答案**：假设每行高 40 像素，滚动到 400 像素时，视口从索引 10 附近开始。RecycleScroller 根据视口高度和前后缓冲区确定渲染范围，用容器撑出整张列表的高度，只把窗口附近的数据绑定到一小组视图，并更新它们的位置。行高不定时，可以用 DynamicScroller 测量实际高度，再修正累计偏移。视图会换绑数据，因此每条记录的编辑状态要按稳定的数据 ID 保存。


### 4. 工程化与性能

#### Q003 · 工程化与性能 · 状态：已分析
**题目**：如果先完成 Web 端功能，后续需要在 App 内嵌 H5 中接入该能力，部分能力依赖 App 原生接口，你们是否遇到过这类场景？如何实现多平台高效迭代、协同上线？
**关联**：Q002 划分模块，本题协调版本发布。
**考什么**：能否处理网页和客户端发布节奏不同造成的兼容问题。
**解题思路**：
1. 先约定能力接口与失败行为，再拆分两端交付。
2. 逐个检查新旧组合，确定开放和回退条件。

**参考答案**：模拟接入原生分享时，我会先和客户端约定参数、回调、取消行为和能力探测方式，让网页通过同一个接口调用浏览器或原生实现。网页先用模拟返回值开发，客户端提供测试包后，再联调分享成功、取消和旧版缺能力的路径。上线时保留复制链接的入口，只对探测到新能力的用户开放原生分享。这样即使用户暂时没升级，或者新接口需要关闭，网页也能继续使用。

#### Q009 · 工程化与性能 · 状态：已分析
**题目**：简历中提到了拆包优化，请介绍前端性能优化以及包体积优化的常见方案。
**关联**：Q011 讨论构建机制，本题验证加载收益。
**考什么**：能否从一次加载的瓶颈判断拆包是否值得。
**解题思路**：
1. 先用网络瀑布和性能记录区分下载、执行与渲染耗时。
2. 结合依赖分析选优化措施，用相同条件复测。

**参考答案**：模拟排查一个首屏很慢的报表页，我会先看网络瀑布和主线程记录。如果首页已经下载了只在导出时使用的表格库，可以把它改成点击导出后动态导入，再检查主包里是否还有其他入口引用它。重复依赖和无用模块则分别从版本归并和 tree shaking 入手。拆完要在相同网络条件下比较首屏传输字节、脚本执行时间和 LCP，也要测首次点击导出的等待时间，确认成本转移到了哪里。

#### Q011 · 工程化与性能 · 状态：已分析
**题目**：你同时使用过 Vite 和 Webpack，讲一下二者的区别。
**关联**：Q009 讨论包体积，本题比较工具机制。
**考什么**：能否区分开发服务器怎样供给模块，以及生产产物如何组织。
**解题思路**：
1. 沿着冷启动、修改模块和浏览器更新的路径比较。
2. 再说明生产构建和迁移成本，注明版本或配置前提。

**参考答案**：典型开发模式下，Vite 利用浏览器原生 ESM，浏览器请求到某个源码模块时，开发服务器再转换并返回它，依赖可以预构建。Webpack 通常从入口建立依赖图并编译出可供加载的产物，也支持缓存、增量编译和热更新。生产环境两者都能拆包、压缩和生成带哈希的文件。我会结合实际版本、插件兼容性、冷启动及热更新时间做选择，已有项目还要评估 loader 和构建插件的迁移代价。
